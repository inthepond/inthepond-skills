# Atlas — the judgement juniors don't have yet

Contrasts a senior carries around without thinking about them. Each entry gives the weaker version, the stronger version, why, and when the weaker version is actually fine — because "always do X" is not judgement either.

Use these in the `concepts` lens and wherever another lens needs a good-vs-bad. Before using an entry, find the project's own instance and cite it — the person learns more from their code than from the atlas. Never claim the project does something it doesn't; if it shows the weaker version, say so as an observation with a question, not a verdict.

The list is a starting set, not a boundary. Build new contrasts in the same shape.

---

## Networking

- **Exposure** — weaker: an internal service reachable from the internet, protected by application login or by nobody knowing the address. stronger: internal services not routable from the internet at all (private networking, internal-only ingress), with a single public entry point through a gateway or load balancer. because: every reachable surface is attack surface; defence in depth means one mistake is not a breach. fine when: the API is genuinely public — then authentication, rate limiting, and abuse protection at the edge carry the weight.
- **Egress** — weaker: services can call anything, from any address. stronger: known exit paths (a NAT gateway, a proxy, an allowlist). because: partners allowlist a stable source address, and you can see — and stop — what leaves. fine when: early prototypes with no partners and no sensitive data.
- **DNS changes** — weaker: "the DNS change is live, so everyone sees it". stronger: know the record's TTL and lower it well before a migration. because: resolvers cache the old answer for up to the TTL, so some users hit the old server for hours. fine when: a brand-new name nobody has cached yet.
- **TLS verification** — weaker: turn off certificate verification to make an error go away. stronger: fix the trust chain — for example, configure the corporate proxy's CA bundle through the runtime's documented setting. because: disabling verification removes protection against interception everywhere that code ever runs. fine when: never in shipped code.
- **CORS** — weaker: believing CORS protects the server, or answering `*` to make errors stop. stronger: CORS is a browser rule about which origins may *read* a response; it does not stop requests from scripts or servers. Allowlist exact origins. because: real protection is authentication and authorisation on the server. fine when: genuinely public, unauthenticated, read-only resources.
- **Auth failures on API calls** — weaker: an API call from the browser with an expired session gets a redirect to the login page. stronger: API calls get a 401 with a JSON body, and the frontend decides to send the user to login. because: a cross-origin redirect fails in the browser and surfaces as a baffling network error instead of "your session expired". fine when: full-page navigations, where a redirect is exactly right.
- **Latency between hops** — weaker: a request that makes ten network calls one after another. stronger: know the rough cost — about a millisecond within a region, tens to hundreds across regions or continents — and parallelise, batch, or co-locate. because: sequential hops add up, and the slowest one sets the pace. fine when: rare, background work.
- **Connection pools** — weaker: a new database connection per request, or pools sized without arithmetic. stronger: pooled connections, with pool size × instance count kept under the database's connection limit. because: autoscaling multiplies pools, and the database refuses connections exactly when traffic peaks. fine when: one long-lived process with light load.

## HTTP and APIs

- **Status codes** — weaker: `200 OK` with `{"error": …}` in the body. stronger: status codes that mean what they say — 4xx is the caller's problem, 5xx is ours. because: clients, caches, retries, and alerting all branch on the status code. fine when: never for real APIs.
- **404 or 403** — weaker: 403 for a resource the caller may not see. stronger: when the existence of a thing is itself sensitive, answer 404 to unauthorised callers. because: a 403 confirms the thing exists. fine when: existence isn't sensitive — then 403 is clearer for everyone.
- **Long operations** — weaker: hold the request open for minutes. stronger: answer `202 Accepted` with a job ID, then poll or stream the status. because: proxies and platforms cut long requests, and a retry of a half-finished operation doubles the work. fine when: the work reliably finishes in a couple of seconds.
- **Validation** — weaker: trust what the frontend sends because the form validates it. stronger: validate at every trust boundary, on the server. because: anyone can send a request without your form; client-side validation is a convenience for the user, not security. fine when: never skip the server side.
- **Changing a contract** — weaker: rename or reshape a response field in place. stronger: additive changes first, deprecate, then remove; shared schemas or contract tests between the two sides. because: clients you don't control — or that deployed last week — break silently. fine when: you own and deploy both sides in one step.
- **Pagination** — weaker: return every row. stronger: limit plus cursor. because: it works with 20 rows in dev and falls over with two million in production. fine when: the set is small by definition (the days of the week).

## Security

- **Authentication vs authorisation** — weaker: "logged in" means "allowed". stronger: authentication proves who you are; authorisation decides what you may do, checked on every action. because: most real breaches are one user reaching another user's data while fully logged in. fine when: never conflate them.
- **Hiding vs enforcing** — weaker: hide the button from users without permission. stronger: the server refuses the action; hiding is only a courtesy. because: requests can be sent without the UI. fine when: hiding is fine *in addition to* enforcement.
- **Fail closed** — weaker: if the permission check errors, let the request through. stronger: deny on error, and report it as what it is. because: an outage in the permission system must not become an open door. fine when: degrading a non-sensitive, read-only feature.
- **Flags vs permissions** — weaker: gate who may do something with a flag. stronger: flags control rollout; permissions control access. because: flags are usually environment-wide, often visible to clients, and flipped by people thinking about rollout, not security. fine when: never as the only control.
- **Secrets** — weaker: in code, in a committed `.env`, in logs, or in infrastructure state. stronger: a secret manager, injected at runtime, rotated, never logged; infrastructure creates the container, a human or a pipeline sets the value. because: anyone with access to the repo, the logs, or the state file has the secret. fine when: throwaway local secrets with no reach.
- **Tokens in the browser** — weaker: access tokens in `localStorage`. stronger: `HttpOnly`, `Secure`, `SameSite` cookies; browser apps sign in with authorization code plus PKCE rather than the old implicit flow. because: any injected script can read `localStorage`. fine when: never for real user sessions.
- **Least privilege** — weaker: one powerful identity for every service and pipeline; long-lived keys in CI. stronger: an identity per service, grants per caller-and-callee pair, short-lived credentials (workload identity federation instead of stored keys). because: a compromise is limited to what that one identity could do. fine when: a solo prototype — and even then, not for long.
- **Injection** — weaker: string-built SQL, shell commands, or CI scripts with untrusted values interpolated into the source. stronger: parameterised queries; values passed as arguments or environment variables, never spliced into the code itself. because: a crafted input becomes code. fine when: never.
- **Personal data in logs** — weaker: log whole request bodies. stronger: log identifiers and event names; redact. because: logs are copied widely and kept long; they become the leak. fine when: local debugging that never leaves your machine.
- **Supply chain** — weaker: floating versions, unpinned base images, installs that ignore the lockfile. stronger: lockfiles with frozen installs, base images pinned by digest, and an automated process that proposes updates. because: what you tested is then what you ship, and updates happen on purpose. fine when: never in production builds.

## Data

- **Related writes** — weaker: two writes that must both happen, done separately. stronger: one transaction, or a design that tolerates partial failure (an outbox, a reconcile job). because: the process can die between them, and something will eventually be half-done. fine when: the writes are genuinely independent.
- **Migrations** — weaker: rename a column in one release; migrations with no way back. stronger: expand, migrate, contract — across releases — with a real downgrade. because: during a rolling deploy, old and new code run against the same schema at the same time. fine when: a table nothing reads yet.
- **Uniqueness** — weaker: check whether it exists, then insert. stronger: a unique constraint in the database, with the conflict handled; constraints named on purpose. because: two requests can both pass the check. fine when: never for anything that must be unique.
- **Indexes** — weaker: none on the columns you filter by, or one on everything. stronger: indexes for the real queries, checked with the query plan. because: missing indexes are slow reads; needless ones are slow writes. fine when: tiny tables.
- **Source of truth** — weaker: the same fact written in two places. stronger: one owner; everyone else references it, or caches it with known staleness. because: two copies eventually disagree, and nobody knows which is right. fine when: a deliberate cache with a stated staleness rule.
- **Time** — weaker: local-time strings, timezone-naive datetimes. stronger: store UTC with an explicit zone; convert only at display. because: daylight saving, month end, and users in other zones. fine when: never for stored timestamps.
- **Money** — weaker: floating point. stronger: integer minor units (cents) or a decimal type. because: `0.1 + 0.2` is not `0.3`. fine when: never for money.
- **N + 1 queries** — weaker: one query for the list, then one per item. stronger: join, batch, or preload. because: fine with ten items, a timeout with ten thousand. fine when: the list is small by definition.

## Resilience and distributed systems

- **Timeouts** — weaker: library defaults, which are often none or several minutes. stronger: an explicit timeout on every network call, shorter than the caller's own deadline. because: a slow dependency holds connections until the whole service stalls — slow is worse than down. fine when: a one-off script you are watching.
- **Retries** — weaker: retry everything, immediately, forever. stronger: retry only transient failures of idempotent operations, with exponential backoff, jitter, a cap, and a budget. because: synchronised retries turn a blip into an outage — the thundering herd. fine when: never without backoff.
- **Rate limits** — weaker: hit the limit, get rejected, retry. stronger: throttle on your side (a token bucket) to stay under a known upstream limit, and honour `Retry-After`. because: staying under the limit is cheaper than recovering from it; rejections waste capacity and can get you blocked. fine when: the limit is far above anything you will send.
- **Idempotency** — weaker: submitting twice creates two orders. stronger: an idempotency key or a natural unique key; a repeat returns the existing result. because: networks duplicate, users double-click, queues redeliver. fine when: reads, which are idempotent already.
- **Delivery guarantees** — weaker: assuming a message arrives exactly once. stronger: assume at least once, and make consumers idempotent. because: exactly-once is mostly a promise kept by idempotent consumers, not by the queue. fine when: never assume.
- **Caching** — weaker: a cache with no stated staleness or invalidation story. stronger: every cache has a written reason it is safe to be stale for its lifetime, and a key that includes everything the value depends on. because: stale data is a bug users see and engineers cannot reproduce. fine when: values that never change.
- **Degradation** — weaker: one dependency down means the whole page errors. stronger: degrade the feature, not the product — timeouts, fallbacks, a circuit breaker. because: users can live without the recommendations panel; they cannot live without checkout. fine when: the dependency *is* the product.

## Delivery

- **Build once, promote** — weaker: rebuild for each environment. stronger: build one artefact, identify it by digest, promote that same artefact up the ladder. because: otherwise "tested in staging" describes a different build. fine when: there is only one environment.
- **Environment parity** — weaker: code paths that branch on the environment name. stronger: the same code everywhere; only configuration differs. because: production-only branches are code that is only tested in production. fine when: unavoidable local-only shims, kept small and obvious.
- **Pull request size** — weaker: a 2,000-line PR. stronger: small, reviewable increments; unfinished work merged behind a flag. because: review quality falls as size rises — big PRs get rubber-stamped. fine when: mechanical changes (a rename), clearly labelled.
- **Feature flags** — weaker: flags that never die; flags read once at startup by accident. stronger: each flag has an owner and a removal date, defaults off, and is read where it is used. Flags spanning components have a rollout order — enable the provider before its consumers. because: dead flags are hidden complexity, and a consumer switched on before its provider fails. fine when: long-lived operational kill switches, deliberately named as such.
- **Rollback** — weaker: "we'll fix forward" with no rollback path. stronger: a tested, fast rollback (redeploy a known-good artefact), and knowing which changes cannot be undone — migrations, sent emails, external calls. because: under pressure, the fastest safe option should already exist. fine when: never as the only plan.
- **Commit messages** — weaker: "fix", "tidy up", "wip". stronger: the why in the message, with the ticket reference there rather than in code comments. because: the person running `git blame` in two years — possibly you — needs the reason. fine when: commits squashed away before anyone else sees them.
- **Checks** — weaker: "it passed on my machine". stronger: lint, type-check, and tests run in CI on every change, and are required to pass. because: your machine is not the build. fine when: never.

## Operations and observability

- **Logs** — weaker: free-text sentences with values glued in. stronger: structured logs with stable event names, a correlation or trace ID, and levels used consistently. because: you can search and count `event=payment_failed`; you cannot reliably search prose. fine when: local debugging.
- **Logs, metrics, traces** — weaker: logs for everything. stronger: metrics for "how much and how often", traces for "where did the time go across services", logs for "what exactly happened here". because: each answers a different question cheaply. fine when: small systems, where logs alone can be enough.
- **Health checks** — weaker: one endpoint that checks everything, including third parties. stronger: liveness checks only the process; readiness checks what is needed to serve. because: a third-party outage should not restart your whole fleet. fine when: never mix them.
- **Alerts** — weaker: an alert on every cause, routed to a busy chat channel. stronger: alerts on symptoms users feel, each linking a runbook and a dashboard, tested, and routed somewhere that wakes a human for the highest severity. because: noisy alerts get ignored, and nobody is woken by a busy channel. fine when: low-severity, informational notices.
- **Silence** — weaker: alert when an error counter crosses a threshold. stronger: also alert when the signal disappears (a heartbeat, a "no data" condition). because: a counter that stops being emitted never crosses anything. fine when: the signal cannot disappear.
- **Error reports** — weaker: catch, log the message, move on. stronger: error reporting with the release, the request, and the user impact attached. because: the first question in an incident is "since which release?". fine when: errors that are expected and handled.

## Code and design

- **Cohesion** — weaker: one feature change touches nine files across five modules. stronger: things that change together live together. because: scattered changes are where bugs slip in. fine when: genuinely cross-cutting concerns.
- **Abstraction timing** — weaker: a shared helper after the first duplication. stronger: tolerate duplication until the shape is clear — often the third time. because: the wrong abstraction costs more than the duplication it removed. fine when: the abstraction is already well understood (a date-formatting helper).
- **Errors** — weaker: empty `catch` blocks; one generic "something went wrong" for everything. stronger: handle an error where you can do something about it; otherwise propagate it with context. Never report one failure as another — a permission refusal shown as a network error sends responders down the wrong path. because: swallowed and mislabelled errors are where incidents hide. fine when: ignoring an error is a deliberate, commented decision.
- **Missing configuration** — weaker: silently fall back to `localhost` or a default when a required setting is missing. stronger: fail loudly at startup outside local development. because: a silent fallback in production is an outage that looks like success. fine when: local development defaults.
- **Comments** — weaker: comments that restate what the code does. stronger: comments that say why — constraints, rejected alternatives, the incident that caused the line. because: code shows what; only people can say why. fine when: what-comments in genuinely dense code (a regex, bit manipulation).
- **Layers** — weaker: business rules in controllers, UI components, or SQL strings scattered around. stronger: rules in one place, with input/output at the edges behind interfaces you can fake in tests. because: rules you can test without a network are rules you can trust. fine when: a small script where the layering would outweigh the logic.

## Testing

- **Shape** — weaker: mostly end-to-end tests, or only unit tests. stronger: many fast unit tests, fewer integration tests, a few end-to-end tests of critical journeys. because: speed and flakiness grow as you go up. fine when: very thin apps, where integration tests carry most of the value.
- **Behaviour vs implementation** — weaker: tests that assert which internal function was called. stronger: tests that assert observable behaviour. because: implementation tests break on every refactor and miss real bugs. fine when: verifying a call to an external system you must not actually hit.
- **Fakes and mocks** — weaker: mock everything, so tests pass while production fails. stronger: fakes for your own interfaces, real dependencies (containers, emulators) in integration tests, contract tests with services you don't own. because: a mock only agrees with your assumptions. fine when: a mock at the boundary of a third party you cannot run.
- **Flaky tests** — weaker: re-run until green. stronger: quarantine, then fix or delete. because: a flaky suite teaches everyone to ignore red. fine when: never as a habit.
- **Coverage** — weaker: chase a percentage. stronger: cover the risky paths, especially the unhappy ones. because: coverage shows what ran, not what was checked. fine when: a floor that stops coverage silently falling.
- **Bugs** — weaker: fix the bug and move on. stronger: write the failing test first, then fix. because: it proves the fix, and the bug cannot quietly return. fine when: the bug is untestable by nature — then say so in the PR.

## Working with coding agents

- **Shipping what you can't explain** — weaker: accept a diff because it runs. stronger: be able to explain every line you ship — what it does, why this way, how it fails, how to undo it (the `own` lens). because: you are the one on call, not the agent. fine when: never for code you merge.
- **Conventions** — weaker: let the agent invent a convention in every session. stronger: instruction files (`CLAUDE.md`, `AGENTS.md`) that carry the project's invariants, and hooks that run lint and type-checks after each edit. because: mistakes caught in seconds cost nothing; caught in review they cost a day. fine when: throwaway experiments.
- **External text** — weaker: feed tickets, logs, web pages, or PR comments to an agent as if they were instructions. stronger: treat them as data. because: text can contain instructions written by someone else (prompt injection). fine when: never assume text is safe because it came from inside the company.
- **Change size** — weaker: one huge agent-generated PR. stronger: small, scoped increments, each reviewed and understood. because: review quality collapses with size, whoever wrote the code. fine when: mechanical, clearly described changes.
- **Agent permissions** — weaker: agents with your full credentials and access to secret files. stronger: scoped tool permissions; secret files denied to the agent outright. because: an agent that can read a key can leak it. fine when: never for production credentials.
